## Current Workspace Data Model

The canonical strict schema contains profile, tasks, sessions, topics, evidence, plans, quizzes/attempts, materials, decks/cards, exams, events, transactions, goals, focus, notes, notifications, preferences, habits, lesson records, and bounded feedback. It caps high-growth arrays and rejects an entire workspace payload over 4 MB before persistence. The design currently trades database normalization for offline simplicity and whole-workspace conflict merging.

This design is valid only as a controlled interim architecture. It still has three known scale limitations: browser localStorage quota varies by browser and device; serializing the full workspace on every mutation has increasing cost; and same-ID concurrent edits follow active-device local precedence after a revision conflict. A future migration must preserve existing data and introduce versioned IndexedDB local persistence before local workspace size becomes a practical risk. High-growth server records should later be normalized in a staged order: materials metadata, notes, tasks/sessions, transactions, review history, and quiz/evidence records.

## Comprehensive Source-Scan Outcome

The audit searched active client and server source for unresolved markers, public procedures, local/session persistence, direct storage routes, route declarations, mock/sample paths, fallback behavior, and catch/error logging. The only intentional public application procedures are account discovery/logout; health/system framework operations are outside the learner data surface. Current local persistence includes the account-scoped workspace cache plus device-only lesson cache, reminder fire log, focus reminder, layout preference, and short-lived authentication fallback token. Those device-only values must remain free of other learners' workspace records.

The scan confirmed two removal candidates: `client/src/lib/workspaceSync.ts` has no active call site because StoreContext implements the current sync lifecycle itself, and `seedSample`/`buildSampleState` have no active production call site. It also identified `ComponentShowcase` as an unregistered development component, not an active route. Expected source-labelled fallback paths exist for Daily Lessons and the Study Assistant; provider logs show actual Daily Lesson timeouts, so source labelling and retry behavior require runtime proof rather than a success claim.

## Immediate P0 Repair Order

1. Isolate or clear account-specific client query responses during sign-out and account changes, starting with workspace hydration.
2. Replace ambiguous reset behavior with explicit local reset and protected cloud-and-local wipe semantics, including clear confirmation copy.
3. Remove the unused legacy sync helper only after source and tests prove it has no call sites.
4. Add direct regression tests for each repair and then run controlled restoration/isolation/conflict validation.

## Completed P0 Remediation Evidence

The active workspace query is now partitioned by a stable account-derived cache input while server ownership remains derived exclusively from the authenticated context. The session discovery route now transmits identity metadata rather than a duplicate workspace blob. Generic storage proxy access now returns 404 for account-owned study-material and profile-photo paths; approved UI flows use protected owner checks followed by a temporary signed URL. The Settings data surface now distinguishes a non-destructive device-cache refresh from an explicit, revision-safe cloud-and-local workspace deletion. The delete flow ignores late results from pre-delete save requests so intentionally erased state cannot merge back into memory.

The verified-unused legacy sync helper and reachable fabricated sample-planner flow were removed. The post-remediation suite passed **49 test files / 163 tests**; TypeScript passed; production build passed; synthetic direct development-server requests for private material and profile-photo paths returned 404; and the protected workspace route returned 401 without a session. These checks do not replace real second-account or physical-device testing.
