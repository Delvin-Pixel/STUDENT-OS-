### Verified P1 repair — resilient tutor model selection

Study Assistant and Daily Lesson Q&A previously requested `gpt-5-mini` by name even though their other AI surfaces select a compatible model from the server catalog. If that historical identifier was unavailable, the tutor path would use its local fallback despite another compatible server model being available. Both tutor surfaces now prefer an available compatible model in a controlled order and only attach `gpt-5` reasoning parameters to compatible models. If the catalog cannot be reached, they defer model choice to the server default; their existing output validation, token/time limits, local fallback behavior, and source labels remain unchanged. Regression coverage verifies a non-`gpt-5` compatible selection and preserves direct fallback behavior.

The lesson Q&A contract also now honors its validated `wantsMedia` field as well as explicit visual-request wording. This ensures a structured tutor response can request an educational visual even when the learner uses wording outside the narrower keyword pattern, while media-generation failure still returns the text answer alone.

The AI resilience increment passed **86 Vitest files / 283 tests**, TypeScript checking, the source credential-literal scan, and the production build. The production bundle still reports the pre-existing 767.31 kB main JavaScript warning before gzip; this repair does not claim a performance resolution. Live provider catalog, model response, image generation, and device acceptance remain manual boundaries.

### Proposed trusted-assessment contract

The future migration should begin in `drizzle/schema.ts`, followed by generated and reviewed SQL applied through the schema workflow. An `assessment_sessions` table should hold an opaque server ID, owner `openId`, source quiz reference, topic/exam references where applicable, status (`in_progress`, `submitted`, `graded`, `expired`), an immutable question-set version, start/submit/finalize timestamps, bounded question count, and a unique owner-scoped idempotency key. An `assessment_questions` table should snapshot prompt, options, correct option, explanation, and ordering for that session. `assessment_responses` should be unique per session/question and hold only the learner selection plus an updated timestamp. The server should grade the immutable snapshot in one transaction, write result fields to the session, and make retry responses idempotent.

The protected API sequence should be `create → resume/read → save response → submit`. Every query and mutation must derive ownership from `ctx.user.openId`; neither the browser's cache scope nor a workspace-provided account ID may authorize an assessment. After server grading, the browser can reconcile a **read-only result summary** into the canonical workspace as learning evidence. It must not accept a browser-provided score as trusted or overwrite an existing server-finalized result. The legacy practice runner can remain available offline, but its UI and evidence must stay labelled provisional/local practice.

### Proposed curriculum-provenance contract

The lowest-risk profile change is an optional `curriculumContext` that adds country, education-system ID, catalogue ID/version, and an optional mapping from existing subject labels to provenance. Existing profiles remain valid because the current `subjects` labels are untouched. The client type, `shared/workspaceSchema.ts`, empty-state/default migration, cloud payload validator, and profile patch path must all change together; the workspace schema version must advance only with a tested compatibility transform for cached older blobs. A catalogue entry should carry a stable subject ID, display label, applicable education bands, source URL/title, retrieval/review date, and catalogue version. It should never infer an official subject from a custom label or an LLM response.

The two migrations should not be combined. Curriculum context can remain workspace-backed and optional. Trusted assessment requires server authority and relational persistence, so it must be planned, migrated, tested for ownership/idempotency/retry, and rolled out separately. This separation preserves the single StoreContext local-first model and avoids describing an unbuilt server assessment as already canonical.

## PWA, offline, and authenticated-session boundary audit

The installed-app cache uses network-first navigation and code loading with offline fallback, while excluding `/api/` and `/manus-storage/` from the device-wide Cache API. Push payload URLs are constrained to the current origin before a window is opened or navigated. The app registers the worker with `updateViaCache: "none"`, so a subsequent online launch revalidates the service-worker script rather than indefinitely retaining a prior app shell.

Workspace hydration is account-scoped at every source-controlled layer: the application remounts `StoreProvider` by authenticated `openId`; React Query includes a display-only account cache scope; browser state and revision metadata use encoded `openId` keys; and server workspace operations derive authorization only from `ctx.user.openId`. A clean remote copy supersedes an idle local cache, while pending offline work remains local until it can sync. Revision conflicts merge canonical collections with tombstone protection; cloud persistence strips device-private AI answer ratings before writing.

### Verified P1 repair — cookie-only application session boundary

The browser previously forwarded a runtime-injected `sessionStorage` bearer value whenever it existed, and the server accepted that bearer value whenever the regular cookie was absent. Although intended for embedded previews, this made a browser-readable session path available outside the normal cookie boundary. The repair removes that fallback entirely: the client never reads or forwards a runtime session-storage token, and the server authenticates application requests only with its signed session cookie. Direct regressions now prove that a valid bearer-only session is rejected and a valid cookie remains accepted even when a bearer header is present. The normal nonce-bound OAuth flow is unchanged. Full release validation passed **86 Vitest files / 285 tests**, TypeScript, the source credential-literal scan, and the production build. The main chunk remains 767.10 kB before gzip, so this repair does not claim a performance resolution.

## Canonical quiz finding

`client/src/pages/Quizzes.tsx` already uses one canonical `StudyQuiz` collection, with manual and reviewed AI sources represented as metadata rather than separate persistence systems. Attempts and learning evidence are handled through the canonical store. The current runner supports question navigation and completed-attempt records, but the directive’s exact **50-question**, durable in-progress recovery, server-authoritative scoring, and detailed grade-band requirements are not yet satisfied by this local-first implementation. A migration must preserve existing quiz attempts and avoid a parallel assessment engine.

The current `scoreQuiz` helper calculates a bounded percentage from canonical question answer keys, but it executes in the client. This is suitable only for local-first provisional feedback; it does not meet the directive's requirement for server-authoritative results. Any migration must add a protected account-owned submission contract and an idempotency key, then reconcile the accepted result back into the canonical workspace rather than trusting a browser-provided score.

The protected tRPC router currently exposes AI quiz **draft** generation but no quiz-session creation, submission, or grading procedure. This confirms that server-authoritative quiz migration is architectural work, not a label change: it needs an explicit protected API and persistence/idempotency design before the UI can represent a result as trusted.

The current relational schema persists users, push state, AI rate limits, and material metadata; canonical quizzes remain in the revisioned account workspace. There is no relational quiz-session, response, or idempotency table today. Any database migration for trusted 50-question sessions must therefore be schema-first, account-scoped, and backward-compatible with existing workspace quiz history.

The shared workspace validator is strict and currently permits only basic profile subjects/level fields plus workspace-local quizzes and attempts. Country, education-system, catalogue provenance, and any draft/session recovery fields must be added to the shared type and validator together, with backward-compatible optional defaults, before they can safely survive cloud synchronization.

### Ghana source evidence for a future verified catalogue

The National Council for Curriculum and Assessment describes Ghana's basic-education phases and lists Standards-Based Curriculum subjects including English, Mathematics, Science, History, Creative Arts, Religious and Moral Education, Physical Education, French, Ghanaian Language, and Computing.[^nacca] Its official Standards-Based Curriculum page publishes the subject catalogue and associated curriculum resources for those foundational bands.[^subjects] The Ministry of Education curriculum microsite separately lists a broader Year 1 secondary catalogue, including Mathematics, Biology, Chemistry, Physics, Computing, Economics, Geography, Accounting, technical/vocational pathways, and languages.[^moe]

These sources support a **Ghana verified** catalogue seed only. They do not verify a universal curriculum, a learner's exact school offerings, or topic-level mappings for every level. Any additional learner-entered subject must remain marked as custom rather than official.
