## What the feature actually does

A signed-in student can submit a bounded Ghana-specific academic profile
candidate through `academicContexts.propose` and retrieve the most
recent version through `academicContexts.latest` or up to ten recent
immutable versions through `academicContexts.versions`.

Each route is protected by the current session and rejects an
`expectedAccountId` different from `ctx.user.openId` **before**
database access. Scheduled cron identities cannot access these routes.

The server derives the database owner from the authenticated session,
generates a random candidate identifier and records the fields in the
additive `academic_context_candidates` MySQL table. The client cannot
set `openId`, authority flags, approval provenance, academic policy
bundles or mastery status.

Supported fields: country GH, level JHS/SHS/TERTIARY, enrollment mode
institutional/remedial/private_candidate/transfer, institution (required
for institutional enrollment), programme (required for tertiary),
curriculum ID/version, optional qualification, academic year and study
period.

The record is **learner-declared**, not proof of school enrolment,
curriculum authorization, source review, independence of assessment,
verified learning, admission eligibility, or official academic policy.

All results explicitly require:
- `provenance: "learner_declared"`
- `authorityStatus: "unverified"`
- `academicPolicyApproved: false`
- `verifiedMasteryEligible: false`

The account owner and idempotency retry key are never returned.

## Durable behavior

- Candidate creation is append-only; new profiles create new versions.
- Repeating a request under the same owner and retry key returns the
  already-inserted version when the content is identical.
- Reusing a key with different content fails with `CONFLICT`, and
  parallel retry races cannot silently overwrite existing records.
- Different accounts can independently use the same retry key.
- Latest/history queries always filter by the session-derived `openId`;
  they do not expose candidates from another account.
- An unavailable database fails closed; no workspace or client cache
  fallback is treated as a server-owned academic record.

The migration was generated using the existing pinned Drizzle toolchain,
not handwritten. It is additive and introduces a new table only;
existing learner workspace, assessment, account and subscription tables
are unchanged.

## NEXA handoff (Track B)

`toAdvisoryAcademicProjection` is a minimal, strictly typed projection
containing only the curriculum-level teaching preferences required for
conversational personalization. It includes no owner, institution,
school year, session token, grades, evidence, policy approval or
permissions.

This is **not** a trusted `AcademicContextSchema` object with a
validated policy bundle and cannot be used to grant official mastery.
Future server-only integration may retrieve the owner-scoped candidate,
build the sanitized advisory projection and pass it to an *advisory-only*
NEXA request, with the B62 deterministic engine authoritative.

Track B should not independently wire a route or authorize academic
writes based on this contract until integration review.
