## Implemented

`client/src/lib/offlineWorkspaceRebase.ts` exports `proposeOfflineWorkspaceRebase`. It composes the existing B64.3 canonical inventory and B64.1 three-way preflight; it does not create a second synchronization authority.

A proposal is returned only when preflight classifies the snapshots as `rebase_required` with no competing-record conflict. The proposal contains:

- A cloud-projected candidate workspace.
- The exact remote revision that must be used as the expected revision for a later server compare-and-swap.
- A bounded list of paths where both peers contributed disjoint changes.
- Explicit `writesPerformed: false` and `requiresRevisionCheckedWrite: true` markers.

The pure merge recursively combines object fields and ID-keyed record arrays when the existing three-way preflight has already established that the changed records are disjoint. It retains remote ordering and deterministically appends local-only records. It does not concatenate arbitrary arrays or guess at non-ID collection semantics.

Deletion markers are treated as durable evidence: the proposal unions base/local/remote tombstones, never silently drops a marker, and deterministically selects the earliest ISO timestamp if the same marker appears more than once. Device-private AI answer ratings are excluded from the cloud projection; expiring profile-photo and study-material signed URLs are blanked.

## Fail-closed behavior

The function returns a held result instead of a proposal for:

- Wrong or changing authenticated account identity.
- Invalid workspace/schema or unavailable digest/preflight.
- Stale or otherwise invalid snapshot/revision.
- Competing edits to the same record.
- Delete-versus-edit or tombstone resurrection/missing-marker conditions.
- Scalar/root conflicts. B64.3 intentionally fingerprints aggregate scalar state, so B64.4 does not infer that two scalar changes are independent.
- Unsupported non-ID arrays, malformed/duplicate ID arrays, recursion/node limits, or any merge result that fails schema/semantic validation.
- Any preflight outcome other than `rebase_required`. Local-only revision writes and remote-only adoption remain separate workflows.

A proposal is **not** a write authorization, authenticated ownership proof, signature, encryption, academic decision or server revision. SHA-256 remains a change-detection mechanism only. A future call site must fetch base and remote snapshots through owner-scoped server APIs, derive account identity from verified authentication, cancel work on session-epoch changes, and submit only through the existing server-side revision-CAS contract. The app must reattach device-private feedback locally after any cloud projection as appropriate.

## Tests added

`client/src/lib/offlineWorkspaceRebase.test.ts` adds nine regression cases:

1. Disjoint local/remote record additions combine without mutating inputs.
2. Edits to different nested flashcards combine while retaining parent identity.
3. Competing edits to the same record are held for manual review.
4. Delete-versus-edit is held rather than resurrecting a record.
5. Tombstones survive while a disjoint remote addition is proposed.
6. Scalar/root conflicts remain held.
7. Device-private feedback and transient signed URLs are excluded from the cloud proposal.
8. Account mismatch is blocked.
9. Unchanged snapshots do not produce a rebase or write authorization.
