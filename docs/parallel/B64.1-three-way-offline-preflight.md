# B64.1 — Offline synchronization three-way conflict preflight

**Track:** B — independent offline/reliability engineering. **Status:** Pure, unwired client-side conflict classifier. This is not a new synchronization engine or live data migration.

## Why this is needed

The existing Student OS cache uses account-scoped `localStorage`, revision-checked server writes, durable tombstones and `mergeWorkspaceStates`. During a revision conflict, that merge intentionally prefers local changes for the same item ID and scalar fields. Because it lacks an acknowledged _base snapshot_, a remote-only edit to an otherwise unchanged local record can be overwritten by a local-wins merge.

## New independent contract

`client/src/lib/offlineSyncPreflight.ts` classifies exactly three immutable snapshots:

- **Base:** last server-acknowledged, validated same-account record inventory and scalar digest.
- **Local:** current device inventory, including unacknowledged edits and retained deletion markers, still carrying the acknowledged base revision.
- **Remote:** freshly authenticated server-owned inventory with a monotonically nondecreasing revision.

Inventory entries have a canonical collection, stable item ID, and either a SHA-256 digest for an existing item or a **durable deleted marker**. A root digest covers scalar fields outside the record collections. Full records, credentials and academic content are not returned by the preflight result.

Results: `unchanged`, `adopt_remote`, `ready_for_revision_checked_write`, `rebase_required`, `manual_review`, or `blocked` with a bounded reason. `ready_for_revision_checked_write` **does not perform a write**; callers still require the original authenticated server revision compare-and-increment. `rebase_required` **must not** call the existing local-wins merge without reviewed three-way conflict resolution.

## Fail-closed cases

Reject mismatched account IDs, missing/invalid base inventories, a stale device revision, server revision rollback, malformed or duplicate IDs/digests, changes returned under the same server revision, missing deletion markers, and resurrection of previously deleted records.

Conflicting edits, including delete-versus-edit and concurrently changed scalar settings, require explicit review. Disjoint local/remote edits must be rebased using a separately reviewed algorithm preserving remote changes. Output is capped at 32 conflicts, with a truncation flag; input inventory is bounded to 20,000 entries. Tombstones are **never** compacted by time alone.

## Integration boundary and dependencies

This file is deliberately not imported by `StoreContext`, `storage.ts`, or any server router. It neither creates nor authenticates `accountId`; those values **must** come from established verified authentication and validated workspace ownership. Inventories and hashes must be generated from complete, schema-validated snapshots, not trusted merely because a client supplies a digest.

Track A and Track B must first agree on a canonical inventory serializer (including nested items, private device-only fields, tombstones and root scalars), persist a durable last-acknowledged base snapshot/checksum, and define a conflict UX. No automatic state write or IndexedDB cutover is approved by this milestone.

**Rollback:** Keep draft PR unmerged, or close it. It adds no migrations or production storage writes.

## Remaining B63/B64 path

1. Review and test a canonical hash/inventory extractor against the current `StudyState` schema and validation.
2. Introduce opt-in checksummed account-scoped IndexedDB cache with an **unchanged localStorage read-only fallback** and verified migration/recovery, not a destructive replacement.
3. Add a reviewed, server-revision-checked three-way rebase implementation with same-ID and scalar conflict UX; maintain explicit tombstones until peer acknowledgements permit compaction.
4. Exercise offline/reconnect and account A/B switch scenarios on a lower-end Android device and installed PWA. Measure latency, storage/quota failures and upload size; prohibit background retries during account switches.
5. Do not merge into the main synchronization path before B58.1 live OAuth/DB ownership is validated and cross-branch integration is reviewed.
