## Signed policy governance v1

`shared/academicPolicyAttestation.ts` defines:

- A strict, versioned, domain-separated Ed25519 signed payload with
  document identifier, trusted-registry version, SHA-256 source-manifest
  digest, explicit Ghana curriculum level/version, institution
  restriction (where applicable), and mandatory tertiary programme.
- A published policy metadata bundle with approvedBy, approvedAt,
  publishedAt and issuer authorityId. These fields are signed, but
  *not* sufficient evidence of official institutional approval.
- Detached, independently verifiable signatures by separate publishing
  and reviewing identities. Their roles, principal IDs, public keys,
  validity windows, and authorized academic scopes must match a
  separately vetted server-held trust snapshot.
- Versioned source-manifest review metadata and recorded policy-version
  revocations, including withdrawn and superseded policies.
- A bounded, strictly validated review result that cannot represent
  official approval or verified mastery.

`server/academicPolicyAttestation.ts` checks strict parsing, exact
policy/document scope consistency, approval/publication chronology,
publisher identity and issuer-authority binding, reviewer identity,
independent principals and keys, Ed25519 signatures, registered public
keys, matching curriculum/source SHA-256 digest, source review state,
signer expiration/revocation, policy-version revocation and fresh
trust snapshot metadata (maximum 24 hours).

The payload's canonical signing bytes use explicit v1 domain separation
and strict Zod-defined field order; the signature envelopes themselves
are excluded from the signed bytes. Test fixtures generate ephemeral
Ed25519 keys and never commit signing secrets.

A future server-only handler must load trusted context, trust anchors,
source-review records, revocations and evaluation time from distinct
authorized sources, not from a browser, NEXA, a guessed curriculum
name, an institution dropdown, or self-declared profile data.

## Precise limitation of a passing preflight

Passing verification returns:
- `status: "integrity_passed_not_authorized"`
- `officialApprovalEstablished: false`
- `authoritativeMasteryEligible: false`

A checked signature authenticates its private-key holder **only relative
to the provided public key**. It does not prove that the key holder is
GES, NaCCA, WAEC, an accredited school, a university, a lecturer or any
other legitimate authority. A self-described authority entry can be
cryptographically valid and still be entirely untrusted.

Likewise, a signed source digest identifies content bytes but does not
prove authenticity, coverage, correctness, or academic authorization.
`reviewed` remains a status from the input trust registry; this
module does not independently inspect a real regulator's approvals.

**No client-facing endpoint or policy-publication route is added.**
No approval can be requested or granted merely by importing this
module. There is no migration, DB write, NEXA activation or remote
registry fetch.

## Production-grade authoritative governance prerequisites

Before official policy decisions or mastery can be enabled, provide:

1. **Vetted issuer onboarding:** validate actual Ghana authority and
   tertiary/institutional scope using independently confirmed
   organizational records and human-reviewed authorization; register
   keys via an audited, two-person security procedure.
2. **Protected source ingestion:** verified source content, authoritative
   title/version, licensing, official issuing body, digest preservation,
   replacement/withdrawal procedures and internal review approvals.
3. **Durable revocation and key rotation:** account-independent trusted
   database/versioned event store, authenticated updates, governance
   reviewers, freshness and rollback protection. A client's cached
   revocation snapshot must not authorize newer policies.
4. **Authenticated server trust loader:** pin to a reviewed root of
   trust, restrict key access and write roles, bind issuer and reviewer
   accounts, store immutable audit events, and fail closed when missing.
5. **Publication workflow:** distinct drafting, source review,
   policy review, approval, publication, suspension and revocation;
   immutable policy/version identities and protected reviewer actions.
6. **Student-bound academic context mapping:** associate only approved,
   institution/level/programme-appropriate policies with the
   authenticated account. B62.5's `learner_declared` rows are still
   unverified candidates and must not become approvals implicitly.
7. **Assessment/mastery boundary:** B62.3 learner-origin quizzes remain
   limited advisory evidence. B62.4 mastery decisions remain
   `verifiedMastery: false` until signed, owner-bound, independent
   assessment sources, rubrics, trusted reviewer decisions and the
   durable append-only mastery ledger exist.
8. **Live release-gate verification:** owner-managed B58.1 Student OS
   MySQL credentials, OAuth, protected account isolation, approved
   stage migrations, operational rollback and signed-registry audit.

## Independent adversarial tests and handoff

Tests cover JHS/SHS/tertiary, independent valid signatures, missing
trust anchors, tampering, substitution, mixed roles, wrong authority,
reviewer identity spoofing, dual-key/same-principal attacks, level and
programme mismatches, unreviewed/withdrawn source digests, signer
revocation/expiry, explicit policy withdrawal, stale/future trust
snapshots, malformed records, forged official approval fields,
chronology and canonical signature bytes.

Track B may prepare advisory NEXA explanations of why a policy remains
unverified but must **not** treat this output or B62.5 candidates as an
authorization signal. Work can independently assess trust-loader and
browser caching threat models without implementing a second academic
policy approval workflow.

This PR must remain draft and unmerged. No production key material,
live policy, regulator claim, billing, schema mutation, or automatic
mastery promotion is introduced.
