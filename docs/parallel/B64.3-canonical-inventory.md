# B64.3 — Canonical workspace inventory and three-way preflight handoff

**Track:** B — independent synchronization reliability. **Base:** verified B64.2 commit `ca33bc9afa8fac54cd81501777d8f9d658983885`. No integration into `StoreContext`, `storage.ts`, protected APIs, PWA service worker or production.

## Implemented

`client/src/lib/offlineWorkspaceInventory.ts` builds reproducible, SHA-256 based snapshots from fully schema-validated and semantically checked `StudyState` data.

- Exact account ID and monotonic revision are required. The wrapper rechecks the authenticated owner before and after each awaited computation; a changed owner cannot receive a completed decision.
- All top-level ID-based synchronized collections are covered. Nested deck cards, study-plan items and exam topics become independently addressable entries, with parent IDs included in their digests. Reordering records and object property keys does not create a conflict.
- Stable non-collection fields are digested together as workspace scalars. Habit-log and daily lesson completion sets use sorted canonical order. Existing deletion markers remain explicit `deleted` entries, never automatically expired.
- Existing `projectWorkspaceForCloud` strips private AI answer-rating content from the inventory. Temporary signed study-material and profile-photo URLs are normalized away, preserving durable object keys and relevant academic records.
- Inputs are bounded to 4 MiB and at most 20,000 total inventory records; invalid/unverified workspace shapes and semantic inconsistencies are refused. The snapshot contains only entity identities and digests, not user lesson content.
- `preflightCanonicalOfflineWorkspaceSync` constructs base/local/remote inventories and invokes **the existing B64.1 `preflightOfflineSync`**. It returns only a decision: unchanged, adopt remote, reviewed rebase, manual conflict review, blocked, or a revision-checked-write _candidate_. It never modifies data.

## Important security and correctness boundaries

SHA-256 is for deterministic change detection only. It is **not** account authentication, encryption, a MAC, or evidence of official mastery; a caller must authenticate the account ID and fetch the remote snapshot and last acknowledged base through owner-scoped server APIs. This module neither authenticates a user nor proves that the supplied base was previously acknowledged.

No automatic merge, local database write, remote compare-and-increment, IndexedDB migration, deletion compacting, or background retry has been implemented.

Existing B64.1 conflict handling deliberately holds competing same-ID edits and delete-versus-edit changes. A disjoint edit still requires a reviewed rebase preserving both sides. The present legacy two-way `mergeWorkspaceStates` local-wins merge must not be called as an automatic replacement.

The inventory's root hash includes all remaining scalar/aggregate fields (including foundation checks and academic journey), so those fields will conservatively require human review if both devices edit differently. Derived or device-only fields not explicitly excluded in the existing cloud privacy policy must be examined during integration review; failing closed may over-report conflicts rather than silently discarding data.

## Regression matrix

- Ghana JHS, SHS and tertiary workspaces.
- Deterministic item order and normalized object keys.
- Nested cards, study-plan items and exam topics, including parent movement.
- Preserved durable tombstones; malformed snapshots, duplicate nested keys and cross-owner mismatch rejected.
- Private answer feedback and signed URL rotation must not create phantom cloud conflicts.
- Real three-way: same record updated twice, delete-versus-edit, disjoint changes, unchanged states and stale revisions.
