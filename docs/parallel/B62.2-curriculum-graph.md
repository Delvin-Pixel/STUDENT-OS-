# B62.2 — Versioned curriculum graph and planning-only bridge

## Source checkpoint

Based on the CI-verified dependency-security draft at
`d930f24960d930f495cebe70fa64b45a3b456abc` (draft PR #5).
Changes are additive and isolated; `main`, draft PRs #3–#5, the
B58.1 verified baseline, production, and historical MySQL migrations
remain unchanged.

## Existing authority boundaries

- The existing `client/src/lib/learningIntelligence.ts` remains the
  deterministic learning-estimate and prerequisite-planning engine.
- `shared/academicContext.ts` is the canonical JHS/SHS/TERTIARY
  academic-context shape from B62.1.
- `shared/academicKnowledgePack.ts` describes bounded content-manifest
  metadata but does not verify remote sources or content digests.
- No source manifest, user-provided URL, inferred topic label, or NEXA
  suggestion confers academic authority.

## Additive contracts

`shared/curriculumGraph.ts` establishes bounded candidate manifests
with exact country, level, education system, subject, curriculum
identifier/version, optional institution, and tertiary programme scope.
Every topic carries stable IDs, learning objectives, source references,
and declared prerequisites. The parser rejects duplicate and missing
identifiers, cycles, unsafe reference URLs, oversized manifests, and
unexpected authority claims. It returns **unverified provenance**.

The graph only describes **within-scope** prerequisite relationships;
cross-level transitions or bridges must use future explicitly approved
and versioned contracts, not inferred links.

The `matchKnowledgePackToCurriculumGraph` helper checks shared scope
and topic coverage for planning. A B59 knowledge pack manifest lacks a
`curriculumId`; even a scope match explicitly remains
`not_attested_by_pack`. No downloader, hash checker, institution
approval, or curriculum registry is introduced in this change.

## Planning-only adapter

`client/src/lib/curriculumGraphAdapter.ts` offers an opt-in
`getCurriculumAwareLearningPath` call that projects graph prerequisites
onto existing learner-local `SubjectTopic` IDs **in memory**. It
requires an explicit one-to-one mapping and rejects missing, colliding,
or mismatched scope rather than matching names automatically.

The projected state is never persisted, and the existing
`getLearningPath` function performs the actual deterministic
learning-path calculation. No workspace update, assessment submission,
mastery decision, payment, entitlement, or server authorization change
occurs. The result always marks provenance as unverified.

This adapter is a candidate planning interface **not activated
automatically in any route**. A later server-owned, account-isolated,
approved-registry gate must precede real curriculum activation. Never
use its output to publish verified mastery.

## Verification and release gates

- Shared contract tests: JHS/SHS/TERTIARY, tertiary programme,
  duplicate/dangling/looped prerequisites, source constraints,
  oversize protection, deterministic ordering, context and institution
  mismatch, and B59 knowledge pack correspondence.
- Client integration tests: multi-hop learning path through the
  existing engine, untouched workspace and evidence, mismatched scope,
  missing/colliding local ID maps, unverified provenance.
- Full GitHub verification required: frozen pnpm install, TypeScript
  app/tests/config, ESLint, Prettier, Vitest, build, bundle check,
  migration metadata, clean CI MySQL application, and both dependency
  security audits.
- Successful isolated checks **do not** close B58.1 live DB/OAuth/
  authentication API gates, B59–B61 release gates, or production
  functionality validation. Keep the PR draft; do not merge or deploy
  without the separately authorized release sequence.

## Deliberately out of scope

Official Ghana curriculum ingestion or approval, signed governance
versions, canonical source review, graph persistence, real account
permissions, NEXA-generated curricula, semantic search, offline pack
downloads, digest verification, and migrations.
